# Architecture

Consult Cortex and current architecture pages, then validate affected source and actual runtime flows. Establish constraints, invariants, ownership, data and trust boundaries before proposing a change.

Compare the current design with the smallest viable alternative. Describe interfaces, failure modes, concurrency, consistency, authorization, observability, deployment, compatibility, cost and rollback. Do not invent a service boundary or database because a directory name suggests one.

Produce a decision with evidence, alternatives, tradeoffs, affected modules and verification criteria. Reuse existing architecture decision records if present. Route complex implementation into plan; use blueprint to persist an initial system map and architecture-sync after meaningful changes. Do not replace user-authored architecture docs or duplicate an existing Archify source of truth.
